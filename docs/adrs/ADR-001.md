# ADR-001: Monorepo Structure for the Inventory System

## Context

The Inventory System (invsys) requires independently deployable microservices that communicate asynchronously via a message broker ([PRD §2.6](../PRD.md)). The PRD also mandates a single `docker-compose` command to launch the full ecosystem ([PRD §4, Notes](../PRD.md)).

The team must decide:

1. Which **architecture styles** govern the system.
2. How to **organize the source code** in version control.

### Architecture drivers from the PRD

- Two domain services — Products (CRUD) and Inventory (stock management) — communicating via events.
- JWT-based authentication with role-based access control (`Admin`, `User`).
- Idempotent event processing between services.
- A single `docker-compose.yml` that spins up the entire stack.

---

## Decision

### Architecture Styles

This system combines three complementary styles:

**1. Microservices Architecture** — Three bounded contexts, each as an independently deployable service:

| Service | Bounded Context | Responsibility |
|---------|-----------------|----------------|
| **Auth Service** | Identity & Access | Token issuance, credential management, role assignment |
| **Products Service** | Product Catalog | Product CRUD (name, price, category, SKU) |
| **Inventory Service** | Stock Management | Stock adjustments, movement history, availability queries |

Auth is separated into its own service — even though the PRD only explicitly names two — because token issuance is a stateful operation with its own data store (`users`, `credentials`, `refresh_tokens`). Products and Inventory should not own user data. Token **validation** remains stateless and is shared via `libs/jwt/`.

**2. Domain-Driven Design (DDD)** — Each service encapsulates a bounded context with its own database (database-per-service). No service reads from another's data store. Inter-context communication happens exclusively through events or API calls.

**3. Event-Driven Architecture (EDA)** — One EDA pattern is adopted:

- **Publish-Subscribe** — Producers publish domain events to broker topics (`product.events`, `inventory.events`). Consumers subscribe independently. This directly satisfies the PRD's requirements (§2.6): the Products Service publishes events when a product is created, updated, or deleted; the Inventory Service subscribes and reacts accordingly. Durable subscriptions enable at-least-once delivery with consumer-side idempotency (§2.6.3). New consumers (e.g., a future Reporting Service) can subscribe without modifying producers.

EDA patterns **rejected**:
- **Event Notification** — Adds a synchronous callback (consumer queries producer's API for full details), reintroducing the coupling that EDA is meant to eliminate. The Inventory Service only needs a `productId` to initialize a `StockItem` — it does not need product name, price, or category, as those are not its domain.
- **Event Sourcing** — Over-engineered for simple CRUD + stock adjustments.
- **Event-Carried State Transfer** — Couples consumers to the producer's data model.
- **CQRS** — Query patterns are straightforward and don't require a separate read store.

### Monorepo Structure

```
invsys/
├── services/                    # Backend microservices (bounded contexts)
│   ├── auth-service/
│   ├── products-service/
│   └── inventory-service/
├── apps/                        # Frontend applications (reserved, future)
├── libs/                        # Shared libraries
│   ├── common/                  # Shared DTOs, constants, error handling
│   ├── jwt/                     # Stateless token validation middleware
│   └── events/                  # Event contracts, broker client
├── infra/                       # Infrastructure & orchestration
│   ├── docker-compose.yml       # Core services
│   ├── docker-compose.observability.yml
│   ├── docker-compose.dev.yml
│   ├── .env.example
│   ├── broker/                  # Message broker configuration
│   └── observability/           # Prometheus, Grafana configs (no source code)
├── docs/
├── scripts/                     # Automation tasks (format TBD with tech stack)
└── README.md
```

Key structural decisions:

- **`services/` not `apps/`** — Naming reflects domain semantics (microservices), not tool conventions. `apps/` is reserved for frontend deployables.
- **Migrations inside each service** (`services/{service}/db/migrations/`) — Schema is a domain artifact owned by the bounded context, not a centralized infrastructure concern.
- **Observability as configuration** — Grafana, Prometheus, Jaeger run as Docker images. Only their config files live in the repo under `infra/observability/`.
- **Layered Docker Compose** — Core (`docker-compose.yml`) satisfies the PRD's single-command requirement. Observability and dev overrides are opt-in compose files.
- **Language-agnostic** — No language-specific configs (e.g., `tsconfig.base.json`, `pom.xml`) are included. These will be defined in a subsequent ADR when the tech stack is selected.

## Alternatives Considered

### Polyrepo (one repo per service)

Rejected. Event contracts shared between services would require publishing to a private registry or duplication. Cross-service schema changes would need coordinated PRs across repos. The `docker-compose.yml` would need to reference external build contexts.

### Hybrid (shared library in a separate repo)

Rejected. Reduces duplication but adds a fourth repo, a publishing pipeline, and version coordination — overhead disproportionate to the project's scale.

---

## Consequences

### Positive

- **Domain isolation** — Each bounded context evolves independently with its own data store and migrations.
- **Atomic changes** — Event contract, producer, and consumer updated in one commit.
- **Extensibility** — New consumers subscribe to existing topics without modifying producers.
- **Resilience** — Async Pub/Sub decouples service availability; events persist in the broker during downstream outages.

### Negative

- **Repo size growth** — Mitigated by shallow clones and sparse checkouts.
- **Build times** — Mitigated by graph-aware build tools (Nx, Turborepo).
- **Eventual consistency** — Pub/Sub introduces a window where services may have divergent state. Acceptable for this domain.
