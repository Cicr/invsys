## Context

Following the structural guidelines defined in [ADR-001](ADR-001.md) (Microservices + DDD + EDA), the team must select the programming languages and frameworks for the three bounded contexts: Auth, Products, and Inventory. 

The PRD [docs/PRD.md](../PRD.md) imposes several requirements with hidden complexities:

1. **Currency Conversion (§2.3)**: Pricing endpoints must accept an optional currency parameter, dynamically converting prices using an external API.
2. **Price History (§2.3)**: System must track and query the price history of products.
3. **Caching (§2.5)**: Frequent requests (product queries, rates, stock availability) must be cached.
4. **Testing (§3.4)**: High unit testing coverage is a hard requirement for the deliverables.

The architecture must balance these complexities avoiding over-engineering while satisfying performance and maintainability needs.

---

## Decision

We will adopt a **Polyglot Stack**:

1. **Auth Service and Products Service**: **NestJS** (TypeScript).
2. **Inventory Service**: **Golang** (Go).

### 1. Why NestJS for Auth and Products?

- **Rapid CRUD & API Development**: Products is a REST-heavy CRUD service. NestJS provides structural rigor, decorators, and built-in serialization that accelerates REST API development.
- **Built-in Caching**: NestJS has native integration with `CacheManager` (via Redis), making it trivial to satisfy the caching requirement (§2.5) for product listings and exchange rates.
- **Testing Ergonomics**: NestJS is heavily wired for Dependency Injection and uses Jest natively, making aggressive unit testing and coverage reporting almost effortless (§3.4).

### 2. Why Golang for Inventory?

- **High-throughput Event Processing**: Inventory operations (stock entries/exits) are primarily modified via async Pub/Sub events (Kafka/RabbitMQ). Golang's Goroutines are exceptional at consuming high-volume message streams efficiently.
- **Data Integrity & Concurrency**: Stock adjustments require atomic, thread-safe financial-grade operations. Go's strict typing, concurrent primitives, and lack of hidden "magic" make the Inventory domain more predictable and robust.

### 3. Core Libraries and Components Stack

The structure is supported by the following identified tools:

| Component | Usage in the Stack |
|-----------|--------------------|
| **Kafka** | Message Broker. Handles asynchronous Pub/Sub domain events (`product.events`, `inventory.events`). Delivers durable event streams to guarantee the required idempotent processing. |
| **Redis** | Distributed Cache. Both NestJS and Golang connect to it for caching product queries, external exchange rates, and stock metrics to fulfill the PRD caching requirements. |
| **Jest** | Unit Testing (NestJS). Framework used by Auth and Products services to achieve the mandated high test coverage. |
| **go test** | Unit Testing (Golang). Built-in testing framework utilized by the Inventory service for rigorous event-consumer tests and coverage reports. |
| **Swagger** | API Documentation & Testing. Interactive OpenAPI interfaces implemented within the Auth and Products services for rapid developer onboarding and manual endpoint validation. |

### 4. Database Selection

In adherence to the DDD database-per-service architecture defined in ADR-001, we propose designating a targeted database for each bounded context:

| Microservice | Selected Database | Justification |
|--------------|-------------------|---------------|
| **Auth Service** | **PostgreSQL** | Ideal for enforcing strict relational schemas for user identities, roles, and credential references. |
| **Products Service** | **PostgreSQL** | Easily accommodates complex product catalog queries, JSON fields if needed, and robust ACID properties to maintain correct `price_history` logs. |
| **Inventory Service**| **PostgreSQL** | Perfect for managing transactional, atomic stock adjustments (increments/decrements) and providing structured history of inventory movements. |

### 5. Event Contracts Format

Given the polyglot nature of the architecture, models cannot be shared directly as TypeScript interfaces between TS (NestJS) and Go. As planned in the architecture, **`libs/events`** will utilize schemas defined in a language-agnostic format (e.g., **JSON Schemas** or **Protobuf**). This enforces strict, cross-language event contracts between producers and consumers.

### 6. Addressing the "Hidden Complexities"

#### Currency Conversion: Module vs. Microservice?
Currency conversion **will not be a separate microservice**. It will be a module residing inside the **Products Service**.

**Justification to avoid over-engineering:**
- Extracting it into its own service would mean adding a 4th microservice purely to proxy third-party REST calls.
- The Products Service already owns "Prices". When a client asks for a product in `EUR`, the Products Service simply checks its local Redis cache for the rate. If missing, it fetches the rate, caches it, and converts the price synchronously.
- Adding a network hop over a message broker or gRPC just to do a math calculation (Price * ExchangeRate) degrades latency with zero domain benefit.

#### Price History
The **Products Service** will own the `PriceHistory` entity within its database. Whenever a product is updated and the price differs from the previous value, the service will append a record to a `price_history` table within the same transaction. This is a local domain concern of Products—no async events or external services are needed.

#### Caching Strategy
Both NestJS and Golang will rely on a shared **Redis** instance deployed via `docker-compose.yml`. 
- NestJS (Products) will cache general product lists and exchange rates with TTLs.
- Golang (Inventory) will use Redis to cache available stock quantities.

#### Unit Testing Strategy
- **NestJS**: We will leverage `@nestjs/testing` with Jest tests integrated as part of the monorepo tooling. Mocks for the DB and Cache will guarantee isolated fast runs.
- **Golang**: We will utilize the native `go test` and `go tool cover`. Database repositories will be interfaced, allowing dependency injection of mock layers for parallel testing.

## Alternatives Considered

### 1. Homogeneous Stack (100% NestJS)
Rejected. While using only NestJS reduces context switching, the Inventory Service processes concurrent stock adjustments from events. Go's memory footprint and concurrency model for background Kafka/RabbitMQ consumers outperform Node.js significantly. The polyglot strategy allows us to use the best tool for each specific bounded context.

### 2. Homogeneous Stack (100% Golang)
Rejected. Golang is notoriously boilerplate-heavy for standard REST API endpoints (Products) and Auth configuration (JWT issuance, role guards). It would slow down the development of the CRUD-heavy domains that NestJS excels at.

### 3. Currency Conversion Service (Standalone)
Rejected. Adding a `fx-service` increases infrastructure costs, adds a point of failure, and complicates Docker Compose orchestration just to wrap a basic third-party HTTP call. Treating it as a cached utility within the Products Service keeps the architecture lean.

---

## Consequences

### Positive
- **Best Tool For The Job**: Speedy API dev (Nest) + resilient event processing (Go).
- **Reduced Latency**: Consolidating currency conversion directly into Products prevents an extra network hop.
- **High Testability**: Both languages have premier, integrated unit testing ecosystems reducing the friction to meet the PRD's coverage mandate.

### Negative
- **Context Switching**: Developers must jump between TypeScript and Go within the same monorepo.
