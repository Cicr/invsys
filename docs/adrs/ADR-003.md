# ADR-003: Environment Variable Management

---

## Context

In a monorepo architecture with multiple microservices, managing configuration (`.env` files) can easily become disjointed. 
We have three distinct services (Auth, Products, Inventory) and shared infrastructure (PostgreSQL, Kafka, Redis) orchestrated by `infra/docker-compose.yml`.

Typically, microservices possess their own `.env` files (e.g., `services/auth-service/.env`). However, in a local development context governed by a single `docker-compose`, multiple disjoint `.env` files lead to:
1. **Duplication**: DB hosts and broker ports are repeated across multiple files.
2. **Synchronization Errors**: Changing a port in one `.env` but forgetting it in another breaks inter-service communication.
3. **Complex Local Start-up**: Running the full ecosystem demands managing numerous `.env` files scattered across the directory tree.

We must decide whether to centralize or decentralize `.env` configuration for local development.

---

## Decision

We will use a **Centralized Shared Environment** approach for local development using a single `.env` file located inside the `infra/` directory.

### 1. Single source of truth configuration
All microservices and the `docker-compose` will share the same `infra/.env` file. A template is maintained at `infra/.env.example`.

### 2. Suffix Prefixing for Service Scoping
To prevent configuration collision and maintain clarity over which variables belong to which Bounded Context, variables must be explicitly prefixed by their domain. 
Generic variables like `DB_USER` are prohibited. Instead, the team must use:
- `AUTH_DB_USER`
- `PRODUCTS_DB_USER`
- `INVENTORY_DB_USER`

Shared infrastructure must use a generic prefix:
- `KAFKA_BROKER_URL`
- `REDIS_CACHE_URL`

### 3. Loading Mechanism
**When running via Docker Compose**: 
The `docker-compose.yml` natively parses `infra/.env` (when run from the `infra/` folder). It will pass the necessary subset of these variables directly into the service containers.

**When running services locally (e.g., bare metal Node.js/Go)**:
Automation scripts (to be defined in `scripts/`) will explicitly load physical configuration targets, e.g., `set -a; source infra/.env; set +a` or utilizing tools like `dotenv-cli` when starting applications individually on the host machine.

### 4. Secret Management Best Practices

Handling sensitive values (database passwords, JWT secrets, external API keys) requires distinct treatment from standard environment variables (like ports or hostnames):

- **No Hardcoding in Code or Compose**: Passwords MUST NEVER be hardcoded inside `docker-compose.yml` or source code files. The `docker-compose.yml` must use variable substitution (e.g., `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}`).
- **Local Development (.env)**: Secrets for local development are placed inside the centralized `infra/.env` file. This file is explicitly listed in `.gitignore` and `.dockerignore` to ensure developers never check credentials into source control. A scrubbed `infra/.env.example` provides the template.
- **Production Environments**: The `.env` file is **not used in production**. Production secrets must be injected at runtime using managed platform solutions (e.g., Kubernetes Secrets, AWS Secrets Manager, GitHub Actions Environment Secrets, HashiCorp Vault) or via Docker's native `secrets:` block which mounts secrets securely into memory (`/run/secrets/`).

### 5. Environment State Flags (`NODE_ENV` / `APP_ENV`)

The environment file enforces the runtime profile of the applications through strict toggles (`NODE_ENV` for NestJS / `APP_ENV` for Golang). This drastically alters application behavior beyond just logging:

- **Logging**: In `development`, loggers output verbose, human-readable stdout strings with deep stack traces. In `production`, logging bypasses stdout pretty-printing and forces structured JSON payloads explicitly required for ingestion by Observability stacks (e.g., Loki/Grafana).
- **Framework Optimizations**: Setting `NODE_ENV=production` within NestJS disables substantial runtime development checks, skips debugging middlewares, and vastly improves request throughput. 
- **Security & Error Handling**: In `development`, uncaught exceptions and HTTP 500 errors may reflect full stack traces back to the client for debugging. Setting the flag to `production` natively suppresses these stack traces from HTTP responses to prevent severe security leakage.
- **Swagger / Open API**: Developmental documentation and test harness endpoints will selectively expose themselves or turn off entirely depending on these flags.

---

## Alternatives Considered

### 1. Decentralized (One `.env` per service)
This is the standard for polyrepos but an anti-pattern for our monorepo. It guarantees that generic shared URLs (like `REDIS_HOST=localhost`) must be duplicated inside `services/auth-service/.env`, `services/products-service/.env`, etc. Hand-synchronizing 3-5 `.env` files every time infrastructure changes slows down onboarding and invites constant misconfiguration bugs.

### 2. Tool-Specific Config Management (e.g., Doppler, HashiCorp Vault)
While excellent for production environments, requiring external SaaS tools for basic local development violates the PRD rule requesting simple and functional `docker-compose` usage. Production secrets injected by CI/CD are explicitly out of scope for the local `.env` definition.

---

## Consequences

### Positive
- **Guaranteed Consistency**: Updating `REDIS_PORT` in one place updates it for the cache container and every microservice simultaneously.
- **Improved Developer Experience**: Only one file (`infra/.env`) to copy and configure during local setup.

### Negative
- **Oversharing**: All services can theoretically "see" or read environment variables belonging to other contexts (e.g., Products can read `AUTH_DB_PASSWORD`). Since `.env` is exclusively for local development, this lack of security isolation is structurally acceptable, provided we enforce boundaries during code reviews. Production deployments will use properly scoped secrets injection.
